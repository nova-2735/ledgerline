# Assumptions

## Business and scope

- A1. The buyer is Kestrel Foods Pvt. Ltd., a fictional mid-size food manufacturer in Bengaluru (Karnataka, GST state code 29): one GSTIN, one legal entity, INR only.
- A2. Invoices arrive by email as PDFs. In this build they arrive by upload or from the demo inbox; there is no real email intake.
- A3. The "procurement system" is a set of spreadsheet exports: vendor master, PO lines, goods receipts (GRNs) and the ledger of invoices already processed. They are generated as CSV and loaded into SQLite by the seed step.
- A4. Goods POs use a 3-way match (invoice ↔ PO ↔ GRN); service and subscription POs use a 2-way match.
- A5. Default tolerances: unit price ±2%; header amount the lesser of 2% or ₹2,500; round-off up to ₹1; charges without a PO line up to ₹500 allowed as a note; quantity tolerance 0.
- A6. Auto-approval limit is ₹5,00,000 including tax; above it a controller approves even when everything matches.
- A7. GST slabs are 5% / 18% (GST 2.0, effective 22 Sep 2025). Intra-state supply → CGST + SGST; inter-state → IGST. Place of supply is the buyer's state (29) for all demo POs.
- A8. An invoice counts against a PO's billed balance only once it is approved (automatically or by a person).
- A9. A PO reference that isn't printed may be inferred, but the default policy asks a person to confirm it with one click (configurable).
- A10. A changed bank account on an invoice is never auto-approved and never answered by email to the address on the invoice; it needs a call-back to the number on file.
- A11. "Return to vendor" means the document is defective and must be re-issued; "Reject" means it must not be paid (duplicate, blocked vendor, not an invoice).
- A12. Payments are out of scope; "Approve" produces a posting payload (what would go to the ERP).
- A13. Dates in the demo world are fixed around November 2026; tests and the demo use `APP_TODAY=2026-11-20`.
- A14. Free-tier model quotas are tight, so model readings are cached by file hash and cached runs are labelled.

## Added during the build

- "Today" is the Asia/Kolkata business date; with `APP_TODAY` set, `clock.now()` keeps the real time of day but pins the date to `APP_TODAY` (IST), returned in UTC.
- Reader output shapes (`Word`, `PageRead`, `DocumentRead`) live in `backend/app/models/extraction.py`; `ingest/reader.py` produces them.
- Money fields (amounts, unit prices, totals, tax) are 2 dp `Money`; quantities, rates and percentages are exact decimals; both travel as JSON strings and floats are rejected.
- Money is stored in the database as integer paise so SQLite sums stay exact.
- Audit export shape is `{run: RunDetail, events: RunEvent[], raw_model_output}`.
- Demo world: street addresses for all vendors and Om Sai Traders (plus Om Sai's phone and bank) are invented; SCENARIOS gives only city and state.
- Demo world: routine-PO details SCENARIOS leaves open are assumed — SW-NIM-SUP / SW-NIM-ANL use SAC 997331, hair nets HSN 6505, FM-DC-01 SAC 998533 with unit "Job".
- Print style: only V004 and Om Sai print totals with "/-"; V009 prints "Rs. 47,250.00" (per-vendor table in SCENARIOS §3 wins over the template note).
- Print style: line GST rates are printed only by the `modern` template, item codes only by `classic_gst` and `modern`; no template prints a due date, so these are null in truth.
- Ground truth: `raw.total` includes the currency mark as printed (e.g. "Rs. 1,16,348.00", "INR 472,000.00"); `raw.po_reference` is the value after the label; printed notes and notices are listed in `annotations` with stamps and handwriting; `legibility` is "clear" for every document.
- Ground truth: H19 is a byte copy of H14, so `truth/index.json` maps their shared sha256 to H14.
- With no font carrying ₹ (INVOICE_FONT_PATH unset and no DejaVuSans), every "₹" vendor prints "Rs."; generator output is byte-identical across runs on the same machine and font set.
- Scan rotation follows PIL: positive degrees rotate counter-clockwise.
- Intake: `store_document` returns a `StoredDocument` (id, sha256, filename, page_count, path, created); CONTRACTS names the return type `Document` without defining it. Filenames are reduced to their base name.
- Intake: PDFs with only an owner password (no user password) are also rejected as `encrypted`.
- Reader: a page is `scanned` only when it has < 30 characters of text and images covering > 50% of it; a blank page counts as digital. `read_bytes()` sits beside `read_document(path)` for in-memory reads.
- OCR: Tesseract is found on PATH or at the default Windows install folders; with `OCR_ENABLED=1` and no Tesseract, reading a scanned page raises `OCRUnavailableError`.
- Confidence: the `date_valid` validator passes for any date that parses under the DMY rule; an ambiguous day/month only adds a note (otherwise numeric dates such as S01's 12/11/2026 could never reach high confidence).
- Confidence: fields without a validator in CONTRACTS §11 get these — subtotal = sum of lines, round-off and total = arithmetic, amount in words = matches total, buyer GSTIN = checksum, IFSC = format; plain text fields (names, phone, PO reference) have none and top out at medium.
- Extraction: a line that doesn't print its own tax rate takes the document's single effective GST rate (IGST, or CGST + SGST); `TaxSummary.rates_pct` lists effective GST rates (CGST 9% + SGST 9% → 18).
- Extraction: `extract()` returns `ExtractResult(extraction, events, detail)`; events are `stage.log` drafts that the pipeline numbers and timestamps.
- LLM: cache hits keep the original token counts with `cached=true`; the hourly budget counts only live (non-fake) calls, per process; Gemini output tokens include thinking tokens.
- LLM: the fake provider's `map_lines` returns no suggestions and `polish` returns the summary unchanged.
- Reference lookups take the database session as their first argument (`resolve_vendor(session, extraction)`, `Ledger(session).balances(po)`), so callers control the transaction.
- PO inference amount component: overshoot % is measured against the PO's remaining value (ordered − billed, × PO price), not against the 2% headroom; a PO with nothing left to bill scores 0.
- PO inference with an unknown vendor scores the 20 most recent open POs (by PO date).
- Price comparison for tax-inclusive lines uses the pre-tax unit price (taxable amount ÷ quantity).
- Duplicate-check ledger rows are taken within `window_days` either side of the given date (default today); rows without an invoice date are always kept.
- Rules: warnings carry no outcome hint (they never decide an outcome); each per-row matching rule reports one pass summarising the rows that passed plus one result per row that didn't.
- Rules: a missing supplier GSTIN (with a supplier name present) fails T01 as `GSTIN_INVALID`; no GST charged at all skips T03/T04.
- Rules: a confirmed PO keeps the original `PO_INFERRED` / `PO_AMBIGUOUS` / `PO_MISSING` / `PO_NOT_FOUND` result, marked resolved by review.
- Matching: a bundled invoice line bills the full ordered quantity of each PO line in the bundle; header amount at risk is |Σ (row difference × (1 + PO GST rate))|.
- Matching: unmatched rows carry `matched_by="fuzzy"` (the contract has no "none" value); model line-mapping suggestions are accepted only for one-to-one and bundle groups.
- Policy: `policy_version` is written as `<version>+<8 hex>`, e.g. `2026-11-20.1+1a2b3c4d`.
- Decision: `evaluate()` returns the decision plus the checks with the A01 result appended (pass, fail, or skip when the invoice isn't otherwise approvable); `decide()` returns just the decision. `primary_reason` is the first ordered reason, so an approval with notes names its first warning.
- Decision: `redecide(ctx, policy)` re-runs every rule on a copy of a stored run's rule context; the caller builds that context (and leaves the run's own billing out of the ledger).
- Handoff: a REJECT or RETURN also gets a handoff (reopen / not-duplicate / send-to-vendor); codes without a template in RULES §4 fall back by route (vendor → corrected-invoice request, internal → approve-or-reject question).
- Drafts: a RETURN always drafts a vendor email when the vendor is in the master; unknown vendors never get one (there is no master address); internal notes go to the role (Treasury, Receiving, Procurement, or "Buyer — <PO buyer>").
- Posting: a small unmatched charge allowed without a PO line is posted to the first matched line's GL account; per-line GST is computed at the PO rate, and any rounding difference against the invoice's tax total lands on the last line.
- Explanation polish: the model call made by `polish()` is not logged as a run event here; the pipeline does that when it calls `explain`.
- Intake: a file that fails the upload checks (not a PDF, damaged, encrypted, over `MAX_UPLOAD_MB` or `MAX_PAGES`) is refused by `POST /runs` with 422 (413 for size) and the reader's code; no run is created and nothing is stored.
- Resume: rule stages before the resume point are re-evaluated quietly with the review overrides, so checks resolved by review show as resolved in the run detail; only the resumed stages emit events.
- Review: approve / reject / send_to_vendor append a reviewer decision version (final). Approve marks the open failing checks as resolved by that reviewer and builds the posting from the stored matching.
- Review: `not_duplicate` and `reopen` are also accepted on finished runs (an automatic duplicate REJECT); `reopen` re-checks from `validate_document` against current reference data.
- Ledger: every decided run has an `invoice_ledger` row (final outcome empty while awaiting review); billing is written on final APPROVE; a bundled row bills each PO line's ordered quantity with the amount split by PO value; a run stops billing while it is re-checked after review.
- Seed: history always uses the offline reader (ground truth) with explanation polish off; reset keeps the model cache and clears saved policy overrides. Documents are de-duplicated by hash, so H19 (a byte copy) shows H14's filename.
- Stats: the window is runs created in the last `days` days (IST); touchless = first decision APPROVE with no review action; `by_reason` / `by_route` use the first decision of runs that were not auto-approved.
- Policy preview: "before" is recomputed under the current policy rather than read from the stored decision, so only the policy change shows; duplicate checks compare against earlier runs only.
- Policy: `PUT /policy` saves overrides to `DATA_DIR/policy_overrides.json`; new runs and `GET /policy` use the YAML plus saved overrides.
- Decision: a check resolved by review can leave a follow-up note on the decision (bank change → update the vendor master via change control before the payment run).
- Eval: runs use explanation polish off, so the live eval measures the model's reading and the deterministic decision only. Truth for subtotal, buyer GSTIN and PO reference is what is printed (normalised); every other field uses the generator's numbers. A 429 that survives the client's own retries makes the harness wait 30 / 60 / 120 s and re-run the scenario; reaching `MAX_LIVE_LLM_CALLS_PER_HOUR` stops the run and marks the rest as not run.
- Eval report: kept to the verdict, the decision table (with the first difference per scenario) and field accuracy; latency, tokens and retries are in the `.json` next to it.
- The ledger lock that serialises rule stages → decide → billing is in-process: the API runs as one process with `WORKERS` threads. Several API processes would need a database-level lock instead.
- A posting's separately printed other charges become one untaxed line on the first PO line's GL account (their GST is already in the stated tax); the round-off, plus any rounding residual up to ₹1, gets its own line. A larger residual means no posting (A02 holds the invoice).
- Because a final APPROVE must carry a posting, a reviewer can't approve an invoice from a vendor that isn't in the vendor master (409 `posting_incomplete`); the vendor has to be onboarded and the invoice re-run first.
- X01 (same file) uses the same duplicate window as X02/X03: earlier runs whose invoice date is within `window_days` of this invoice's date; runs without a date are kept.
- A demo reset waits up to 60 s for in-flight runs and reviews before giving up with 409 `reset_timeout`.
- Container: the image seeds the demo world at build time into `/app/seed-data` (not a configurable setting); on startup, when the SQLite database in `DATA_DIR` is missing, that snapshot is copied in. With an explicit `DATABASE_URL` nothing is restored.
- Container and Render default to `APP_TODAY=2026-11-20` so the fixed November 2026 demo world keeps its expected outcomes; leave it empty in `.env` for the real date.
- The smoke test uses the demo inbox documents (S01, S06) through `/api/demo/runs`; against a live provider each fresh read is one model call (cached readings are reused).
- VENDOR_NOT_FOUND keeps `approve` in its handoff actions (RULES template), but the API refuses it while no vendor record exists; `RunDetail.approval_block` carries the refusal so the UI shows Approve disabled with that reason.
- Dashboard KPIs show "No prior data" instead of a change when the previous period has no runs or the previous value is 0; the "All" period has no previous period and shows a dash.
- README uses the dashboard and inbox screenshots; no live run view screenshot was captured, so the live run view is described in text.
- Reset: `POST /demo/reset` restores the seeded snapshot when one is current and reseeds otherwise; the response says which (`mode`) and how long it took (`duration_ms`). The image's build-time snapshot is always trusted (it was seeded by the same code); a local snapshot is used only while its fingerprint (app code, prompts, YAML specs, policy file, world manifest) matches.
- Reset: the backup API replaces the live database in place rather than swapping the file, so connections held by in-flight requests (e.g. an open event stream) stay valid; uploaded and rendered files on disk are content-addressed and left alone.
